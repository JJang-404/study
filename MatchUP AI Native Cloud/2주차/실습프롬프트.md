## 실습 2-1. SDD로 3-tier 데이터 플랫폼 구축 — 명세 → 클라우드(Terraform)·로컬(K8s) 배포 → 데이터 품질 게이트 (슬라이드 14·15·29·36 통합)


**실습 목표:** 명세 우선(SDD) 방식으로 "3-tier 데이터 플랫폼" 을 하나의 흐름으로 완성한다. ① 명세(spec)를 먼저 쓰고 → ② 동일 명세로 3-tier를 클라우드(Azure/Terraform)와 로컬(WSL2+Kubernetes) 양쪽에 구성하고 → ③ 데이터 계층(DB)에 적재될 데이터의 품질 검증 게이트를 붙여 명세 충족을 검증한다.
<br/>
> **스토리 흐름:** "무엇을 만들지"를 spec에 못 박고 → 같은 3-tier 설계를 클라우드(IaC)와 로컬(K8s) 두 타깃에 동일하게 세우고 → 데이터가 인프라에 들어가기 전 품질 게이트로 걸러낸다. SDD의 명세→구현→검증 사이클을 하나의 설계로 두 배포 타깃에 그대로 적용합니다.

💭 **Claude Code 프롬프트 (SDD → 클라우드·로컬 3-tier → 데이터 품질 통합)**

"고객 이벤트 3-tier 데이터 플랫폼"을 명세 우선(SDD)으로 만들 거야. 하나의 설계를 클라우드(Azure)와 로컬(Kubernetes) 두 타깃에 동일하게 배포한다. 모든 산출물은 `실습산출물/2주차/` 아래에 만들어(폴더 없으면 생성).

[1단계 · 명세(SDD)]
`실습산출물/2주차/spec/platform_spec.md` 에 요구사항과 수용기준(AC)을 EARS 형식으로 작성해줘:

* 아키텍처(공통): web(프런트) · api(앱) · db(데이터) 3계층 + 계층 간 네트워크 분리
* 클라우드 매핑: web=App Service, api=VM Scale Set, db=Azure SQL, VNet·서브넷·NSG(지역=koreacentral)
* 로컬 매핑: web=nginx, api=node, db=postgres (Kubernetes), web만 외부 노출(NodePort)
* 데이터: db에 적재할 이벤트 CSV 품질 기준(결측률<5%, 중복 0, 이상치 IQR, 필수 컬럼 범위) 및 합격 임계치 95%
각 AC에 고유 ID(AC-1 ...)를 붙이고, 각 AC가 클라우드/로컬/데이터 중 어디에 해당하는지 표시해.

[2단계 · 클라우드 IaC (Azure/Terraform)]
1단계 클라우드 매핑대로 Azure 3-tier Terraform을 `실습산출물/2주차/infra/` 에 생성해줘. 변수(지역·리소스 접두어)는 `variables.tf`로 분리하고 각 리소스에 역할 주석을 달아. `terraform validate`로 문법 검증 후 plan 요약을 보여줘(apply는 내가 확인 후 진행).

[3단계 · 로컬 배포 (WSL2 + Kubernetes/kind)]
1단계 로컬 매핑대로 3-tier Kubernetes 매니페스트를 `실습산출물/2주차/k8s/` 에 생성해줘. web=nginx(Deployment+Service), api=node(Deployment+Service), db=postgres(StatefulSet+Service)로 구성하고 계층을 namespace/label로 구분, web만 NodePort로 노출. kind 클러스터(three-tier)에 `kubectl apply` 후 `kubectl get pods,svc`로 모든 파드가 Running인지 확인하고 결과를 `실습산출물/2주차/2-1_k8s_status.md`로 저장해.

[4단계 · 데이터 품질 게이트]
1단계 데이터 AC를 검증하는 `실습산출물/2주차/quality/validate.py`를 pandas로 작성해줘. 결측률·중복·IQR 이상치·범위 규칙을 점검해 항목별 위반 건수와 합격률(%)을 리포트로 출력하고, 임계치(95%) 미만이면 exit code 1로 종료(게이트). 샘플 `events.csv`도 만들어 실행 결과를 보여줘.

[마무리]
각 AC가 클라우드(2단계)·로컬(3단계)·데이터(4단계)로 어떻게 충족됐는지 매핑한 검증 리포트를 `실습산출물/2주차/2-1_sdd_report.md`로 저장해줘.

# 데이터 품질 게이트
pip install -U pandas
python 실습산출물/2주차/quality/validate.py 실습산출물/2주차/quality/events.csv

# 로컬 3-tier (WSL2 + Kubernetes)
wsl --install -d Ubuntu                      # (PowerShell 관리자) 최초 1회
sudo apt update && sudo apt install -y docker.io   # (WSL Ubuntu)
kind create cluster --name three-tier
kubectl apply -f 실습산출물/2주차/k8s/ ; kubectl get pods,svc

# 클라우드 3-tier (Azure/Terraform - 검증 후 배포, 과금 주의)
az login
terraform -chdir=실습산출물/2주차/infra init
terraform -chdir=실습산출물/2주차/infra validate
terraform -chdir=실습산출물/2주차/infra plan -out tf.plan
# terraform -chdir=실습산출물/2주차/infra apply tf.plan   # 확인 후

✅ 검증: ① `spec/platform_spec.md` 에 클라우드/로컬/데이터 EARS AC 작성 → ② `terraform validate` 통과 & plan에 web·api·db·VNet/NSG 포함 → ③ 로컬 kind에 web/api/db 파드 모두 Running (web NodePort 노출), `2-1_k8s_status.md` 저장 → ④ `validate.py` 가 합격률·게이트(임계치 미달 시 실패)를 출력 → `2-1_sdd_report.md` 에 AC↔(클라우드·로컬·데이터) 매핑 완성. ⚠️ 정리: 클라우드를 apply 했다면 `terraform -chdir=실습산출물/2주차/infra destroy`, 로컬은 `kind delete cluster --name three-tier` 로 정리.

```powershell
ni 실습산출물\2주차\spec\ac_otp.md -Force    # PowerShell: 사양 파일 생성
```[cite: 13]

```bash
pytest -q 실습산출물/2주차/tests/test_otp.py    # AC ↔ 테스트 1:1 검증
```[cite: 13]

✅ 검증: 모든 AC가 테스트와 1:1 매핑되고 테스트가 통과(게이트 통과)한다[cite: 13].

## 1단계 · 명세(SDD) — 요약

| 공통 | AC-1 ~ 5 | 3계층 독립 선언 · 적합 런타임 · 네트워크 경계 분리 · web만 외부 접근 · api/db 외부 진입 없음 |
| 클라우드 | AC-6 ~ 16 | `koreacentral` · App Service / VMSS / Azure SQL · VNet+서브넷 3 · NSG 규칙 · 변수 분리 · `validate` 통과 |

## 2단계 · 클라우드 IaC (Azure / Terraform)

`infra/` 구성: `providers.tf`(버전 고정) · `variables.tf`(지역·접두어 등 입력 변수) · `network.tf`(VNet·서브넷·NSG) · `main.tf`(web·api·db) · `outputs.tf`. 모든 리소스에 역할 주석을 달았습니다.

```text
$ terraform validate
Success! The configuration is valid.

$ terraform plan
Plan: 21 to add, 0 to change, 0 to destroy.
```

| 계층 | 리소스 | 비고 |
|---|---|---|
| web | `azurerm_service_plan`(S1) · `azurerm_linux_web_app`(Node 20 LTS, HTTPS only) | web NSG만 `Internet` 80/443 허용 |
| api | `azurerm_linux_virtual_machine_scale_set`(Ubuntu 24.04) · `azurerm_lb` + backend pool · probe · rule | **공용 IP 없음**, api NSG는 web 서브넷(10.10.1.0/24)의 8080만 허용 |
| db | `azurerm_mssql_server` · `azurerm_mssql_database`(S0) · `azurerm_private_endpoint` | `public_network_access_enabled = false`, db NSG는 api 서브넷의 1433만 허용 |
| 네트워크 | `azurerm_virtual_network`(10.10.0.0/16) · `azurerm_subnet` ×3 · NSG ×3 · NSG 연결 ×3 · resource group | 서브넷 10.10.1.0/24 · 10.10.2.0/24 · 10.10.3.0/24 (비중첩) |

- 지역은 `variables.tf`의 `location` 기본값 `koreacentral` 하나로 통제되며, plan 출력도 `location = "koreacentral"` 입니다.
- `ssh_public_key`, `sql_admin_password`는 **기본값이 없고** 외부에서 주입합니다(비밀번호는 `sensitive`). plan에는 임시 값을 환경변수로만 넣었고 어떤 파일에도 저장하지 않았습니다.
- ⚠️ **`terraform apply`는 실행하지 않았습니다.** 따라서 Azure에는 리소스가 만들어지지 않았고, 클라우드 AC는 "선언이 명세와 일치한다"까지만 입증된 상태입니다.

## 🔎 Web → WAS(api) → DB 배포 검증

"배포가 됐다"가 아니라 **계층이 실제로 서로 연결되어 동작하는지**를 확인했습니다.
api 이미지에 db 도달성 확인 엔드포인트 `/dbcheck`(TCP 5432 접속 시도)를 넣었고, web(nginx)은 `/api/`를 api 계층으로 프록시합니다.

```text
외부(호스트) ──:8080──▶ web (nginx) ──/api/──▶ api (node) ──:5432──▶ db (postgres)
                         NodePort              ClusterIP            Headless
```

| # | 검증 | 명령 | 결과 |
|---|---|---|---|
| 1 | 파드·서비스 상태 | `kubectl get pods,svc` | 5파드 `Running 1/1`, web=NodePort, api=ClusterIP, db=Headless |
| 2 | 실제 실행 이미지 | `kubectl get pods -o jsonpath=...image` | web/api = `jjang404/matchup-w2-*:1.2`, db = `postgres:16-alpine` |
| 3 | **DB 자체 기동** | `kubectl exec db-0 -- pg_isready` | `/var/run/postgresql:5432 - accepting connections` |
| 4 | **DB 읽기·쓰기** | `psql` 임시 테이블 create/insert/select | `CREATE TABLE` · `INSERT 0 1` · 조회 `1:web-was-db` |
| 5 | **WAS → DB** | api 파드에서 `GET /dbcheck` | `{"db_reachable":true,"latency_ms":71}` |
| 6 | **WEB → WAS** | web 파드에서 `wget http://127.0.0.1/api/` | `{"tier":"api","runtime":"node v20.20.2",...}` |
| 7 | **외부 → WEB → WAS → DB 전 구간** | `curl localhost:8080/api/dbcheck` | **HTTP 200** `{"tier":"api","db_host":"db.db.svc.cluster.local","db_reachable":true,"latency_ms":9}` |
| 8 | 외부 → WEB 정적 페이지 | `curl localhost:8080/` | HTTP 200 (`web tier (nginx)`) |
| 9 | WEB → DB **직접** 접근 | web 파드에서 `nc -z db.db.svc.cluster.local 5432` | **BLOCKED** (NetworkPolicy) |
| 10 | 대조: db 접근 차단 시 | db에 deny-all 정책 적용 후 `/api/dbcheck` | **HTTP 503** `{"db_reachable":false,"error":"timeout"}` |
| 11 | 복구 | 정책 원복 후 `/api/dbcheck` | HTTP 200 `db_reachable:true` |

**해석**
- 7번 한 번의 요청이 web → api → db 세 계층을 모두 통과했다는 증거입니다. 10번에서 db 경로를 막으면 같은 요청이 503으로 **실패**하므로, 이 성공이 우연이 아니라 실제 연결 때문임을 확인했습니다.
- 9번: web은 db에 직접 닿을 수 없습니다(단방향 인접 통신). NetworkPolicy가 실제로 강제됨은 정책을 **삭제하면 뚫리고(CONNECTED) 재적용하면 막히는(BLOCKED)** 대조 실험으로 확인했습니다.
- 6번을 `localhost`로 하면 `Connection refused`가 나옵니다. web 컨테이너의 `localhost`가 IPv6(`::1`)로 풀리는데 nginx는 IPv4(`0.0.0.0:80`)만 listen하기 때문이며, 서비스 결함이 아니라 시험 주소의 문제입니다(`127.0.0.1`은 정상).

**한계 (정직하게)**
- `/dbcheck`는 **TCP 도달성**까지입니다. api가 SQL을 실행하는 것은 아닙니다(드라이버 없이 표준 모듈만 사용). DB의 쿼리 동작은 4번처럼 `db-0` 안에서 별도로 확인했습니다.
- 이벤트 CSV를 db에 **적재**하는 단계는 만들지 않았습니다(요청 범위 밖).

## 🩺 응답 읽는 법 — 무엇으로 "정상"이라고 판단하나

`ok` 한 단어만 돌려주면 *무엇을 보고 ok인지* 알 수 없으므로, 응답에 **판단 근거**를 함께 담았습니다. (전체 설명: [`2-1_web_tier_guide.md`](./산출물/2-1_web_tier_guide.md))

| 주소 | 확인하는 것 | 실측 응답(10/18 23:08) |
|---|---|---|
| `localhost:8080/` | 계층별 상태를 보여 주는 홈페이지 | HTTP 200. nginx 기본 "Welcome to nginx!"가 아니라 직접 만든 상태 화면 |
| `/healthz` | **web 자체**: nginx가 요청을 받아 직접 응답했는가 | `{"status":"ok","tier":"web","server":"nginx/1.27.5","pod":"web-746b7d44dc-76hmj"}` |
| `/healthz/chain` | **web → api → db 전 구간**: api가 db에 TCP 5432 연결을 시도한 결과 | `status:"ok"`, `checks.db.method:"TCP connect db.db.svc.cluster.local:5432 (timeout 3000ms)"`, `latency_ms:14` |
| `/api/` | api 자기소개 | `{"tier":"api","runtime":"node v20.20.2","db_target":"db.db.svc.cluster.local:5432","hostname":"api-7f95c888c5-zd7xm","explain":{...}}` |
| `/api/healthz` | api 상태 + db 점검 | 위 chain과 같은 상세 JSON |
| `/api/livez` | api **프로세스 생존**만 (db 미확인) | `ok` |

**필드 뜻**
- `hostname` / `pod`: 응답한 **파드 이름**. `/api/`를 6번 요청했더니 `…gqgkh` 3번, `…zd7xm` 3번이 나와 두 파드가 요청을 나눠 받는 것(로드밸런싱)을 확인했습니다.
- `db_target`: api가 접속하려는 `호스트:포트`. `db.db.svc.cluster.local`은 `<Service>.<namespace>.svc.cluster.local` 형식의 클러스터 내부 주소이며 CoreDNS가 IP로 바꿔 줍니다. 5432는 PostgreSQL 기본 포트입니다.
- `checks.db.method`: **db를 어떻게 확인했는지**. 포트에 TCP 연결이 맺어졌다 = postgres가 접속을 받을 준비가 됐다는 뜻입니다(SQL 실행은 아님).
- 응답 코드: `200` 정상 / `503` 일부 의존 대상(db) 장애. db 접근을 막은 실험에서 `503`과 `error:"timeout"`이 나왔습니다.

**`livez`와 `healthz`를 나눈 이유**: 쿠버네티스는 liveness probe가 실패하면 파드를 **재시작**합니다. 여기에 db 확인을 넣으면 db가 잠깐 느린 것만으로 api 전체가 재시작되어 장애가 커집니다. 그래서 probe는 `/livez`(프로세스 생존)만 쓰고, db까지 포함한 `/healthz`는 사람이 보는 진단용으로 둡니다.

## 4단계 · 데이터 품질 게이트

[`quality/validate.py`](./코드/quality/validate.py)가 pandas로 결측률 · 중복 · IQR 이상치 · 범위 규칙을 점검해 항목별 위반 건수와 합격률을 출력하고, 임계치(95%) 미만이면 **exit code 1**로 종료합니다.

```bash
python quality/validate.py --csv quality/events.csv                      # 합격 경로
python quality/validate.py --csv quality/events.csv --threshold 99.9     # 불합격 경로
```

```text
데이터 품질 게이트 — events.csv
총 200행 · 임계치 95.0%

AC         검사 항목                        위반  상태
AC-26      결측률 (<5%)                     0  OK
AC-27      event_id 중복 (0건)              1  FAIL
AC-28      amount IQR 이상치                1  FAIL
AC-29/30   값 범위 규칙                       2  FAIL

[위반 상세]
  - (AC-26) customer_id: 1건 (0.5%)
  - (AC-26) amount: 1건 (0.5%)
  - (AC-27) event_id: 중복 1건
  - (AC-28) amount: 1건 (허용 -49339.4 ~ 136422.7)
  - (AC-29/30) amount: 음수 1건
  - (AC-29/30) event_type: 허용되지 않은 값 1건 (unknown)

총 위반 4건 / 합격률 99.50%
결과: PASS — 임계치 95.0% 충족 (AC-33)        → exit 0

(--threshold 99.9)
결과: FAIL — 임계치 99.9% 미달 (AC-32)        → exit 1
```

> 샘플 `events.csv`(200행)에는 위반을 **의도적으로 4건** 심었습니다. 99.50%는 "검사기가 위반을 잡아낸다"는 증거이지 실데이터의 품질이 아닙니다. 95% 미만 경로(exit 1)는 샘플이 자연 합격하므로 임계치를 올려 실행 경로를 검증했습니다.
> 이 게이트는 CSV 단독 검증이며 db 적재 파이프라인에는 연결하지 않았습니다.

> 실행일 2026-10-18 · pytest 9.1.1 · Python 3.13 · 프로젝트 전용 가상환경(`실습산출물/2주차/.venv`)
> 산출물: [`spec/ac_otp.md`](./코드/spec/ac_otp.md) · [`tests/test_otp.py`](./코드/tests/test_otp.py) · [`otp/otp_service.py`](./코드/otp/otp_service.py)

### OTP 로그인이란?
로그인할 때 **한 번만** 쓸 수 있는 6자리 숫자 코드를 문자/이메일로 보내고, 사용자가 그 코드를 입력하면 본인으로 인정하는 방식입니다. 이 기능이 "어떻게 동작해야 완성인가"를 **코드보다 먼저** 문장으로 못 박은 것이 수용기준(AC)입니다.

### 1. 수용기준 (EARS 형식 · 9개)

EARS는 `When <사건>, the system shall <동작>` 꼴로 쓰는 요구사항 문법입니다. 설계 값은 **6자리 · 유효 300초(5분) · 최대 3회 시도**입니다.

| ID | 구분 | 한 줄 요약 (EARS 원문은 `ac_otp.md`) |
|---|---|---|
| AC-1 | 정상 · 발급 | OTP를 요청하면 숫자 6자리 코드를 만들어 **발송**하고 `SENT`로 응답 |
| AC-2 | 정상 · 검증 | 유효 시간 안에 맞는 코드를 넣으면 `OK` (인증 성공) |
| AC-3 | 만료 | 300초가 지난 뒤에는 **맞는 코드여도** `EXPIRED`로 거절 |
| AC-4 | 잘못된 코드 | 틀린 코드는 `INVALID_CODE` + **남은 시도 횟수** 안내, OTP는 계속 유효 |
| AC-5 | 재시도 초과 | 3번 틀리면 `LOCKED`, 이후 맞는 코드도 거절(새 OTP 요청 필요) |
| AC-6 | 발송 실패 | 발송 서비스 장애 시 `SEND_FAILED`, 검증 가능한 OTP를 **남기지 않음** |
| AC-7 | 재사용 방지 | 이미 성공에 쓴 코드는 `ALREADY_USED` |
| AC-8 | 재요청 | 새 OTP를 요청하면 **이전 코드는 무효** |
| AC-9 | 평문 비저장 | 코드는 **솔트 + SHA-256 해시**로만 저장 |

요청하신 5가지 케이스는 정상 흐름(AC-1·2), 만료(AC-3), 재시도 초과(AC-5), 잘못된 코드(AC-4), 발송 실패(AC-6)로 모두 포함했고, 보안상 필요한 3개(AC-7·8·9)를 더했습니다.
> `ac_otp.md`의 AC-1~9는 OTP 문서 안에서만 쓰는 번호입니다. `platform_spec.md`의 AC-1~33과는 별개입니다.

**경계값이 핵심입니다.** 만료는 `now >= 발송시각 + 300`일 때부터이므로 **299.9초는 유효, 정확히 300초는 만료**입니다. "5분 이내"만으로는 정확히 5분일 때가 모호하기 때문에 명세에 못 박았습니다.

### 2. AC ↔ 테스트 1:1 매핑

| AC | 테스트 함수 | 이 테스트가 확인하는 것 |
|---|---|---|
| AC-1 | `test_ac1_request_sends_six_digit_code` | `SENT`, 발송 1건, 코드 `\d{6}`, 200번 반복해도 6자리, 난수가 7이어도 `000007`(앞자리 0 채움) |
| AC-2 | `test_ac2_correct_code_authenticates` | 1분 뒤 맞는 코드 → `OK` |

- 이 표는 [`ac_otp.md` 7절](./코드/spec/ac_otp.md)에도 있고, `python tests/make_mapping_table.py`가 pytest를 **실제로 실행한 결과**로 채웁니다(결과 칸을 손으로 고치지 않음). 구현에 버그를 심어 돌리면 `8/9 통과`와 `❌ 실패`로 바뀌는 것을 확인했습니다.
- **"커버리지"와 "통과"는 다른 말입니다.** 커버리지 100% = 모든 AC에 테스트가 **대응**한다(1:1). 9/9 통과 = 그 테스트가 **실제로 성공**한다. 버그를 심으면 커버리지는 100%로 남고 통과만 8/9로 떨어집니다.

테스트가 **빠짐없이 · 겹치지 않게** 대응하는지는 `test_every_ac_is_covered_by_exactly_one_test`가 자동으로 확인합니다.
- **기준:** 각 테스트에 `@pytest.mark.ac("AC-n")` 마커를 달고, pytest가 **실제로 수집한 테스트(`session.items`)** 의 마커를 읽어 `spec/ac_otp.md`의 EARS 표(AC 목록)와 비교합니다. 소스 파일을 글자로 훑지 않으므로 주석 처리된 마커나 수집되지 않는 테스트는 세지 않습니다.
- **실패로 처리하는 경우:** ① 테스트가 없는 AC ② 명세에 없는 AC를 가리키는 테스트 ③ AC 하나에 테스트가 둘 이상(1:1 위반) ④ `skip`/`xfail`로 건너뛰는 AC 테스트 ⑤ 명세 6절 표의 함수 이름이 실제와 다른 경우
- **이 검사가 빈 검사가 아님을 확인:** 임시 복사본에 일부러 오류를 만들어 실제로 실패하는지 봤습니다 (원본은 그대로).

| 만든 오류 | 결과 | 검사가 알려준 말 |
|---|---|---|
| AC-5 테스트의 마커 삭제 | 잡음 | `테스트가 없는 AC: ['AC-5']` |
| AC-4 마커를 `#`으로 주석 처리 | 잡음 | `테스트가 없는 AC: ['AC-4']` |
| AC-3 테스트에 `@pytest.mark.skip` | 잡음 | `건너뛰는 AC 테스트: ['test_ac3_…']` |
| AC-7 테스트에 AC-2 마커를 추가로 부착 | 잡음 | `AC 하나에 테스트가 여러 개: {'AC-2': [...]}` |
| 명세에 AC-10을 추가하고 테스트는 안 만듦 | 잡음 | `테스트가 없는 AC: ['AC-10']` |
| 명세 6절 표의 함수 이름을 오타로 적음 | 잡음 | `AC-1: 명세는 test_ac1_typo, 실제는 [...]` |

### 4. "통과했다"를 믿어도 될까? — 변이 테스트

테스트가 한 번에 전부 통과하면 *테스트가 약해서 통과한 것*일 수도 있습니다. 그래서 구현에 **일부러 버그를 하나씩 심고**(임시 복사본에서만, 원본은 그대로) 그 AC의 테스트가 실제로 실패하는지 확인했습니다.

| 대상 AC | 심은 버그 | 결과 | 실패한 핵심 테스트 |
|---|---|---|---|
| AC-1 | 코드가 4자리 | 잡음 | `test_ac1_…` (외 6개 연쇄 실패) |
| AC-2 | 맞는 코드도 거절 | 잡음 | `test_ac2_…` (외 4개) |
| AC-3 | 만료 경계 `>=` → `>` | 잡음 | `test_ac3_…` |
| AC-3 | 만료 검사 삭제 | 잡음 | `test_ac3_…` |
| AC-4 | 남은 횟수 +1 오계산 | 잡음 | `test_ac4_…` |
| AC-5 | 잠금 후에도 맞는 코드 허용 | 잡음 | `test_ac5_…` |
| AC-5 | 최대 횟수 3 → 4 | 잡음 | `test_ac5_…`, `test_ac4_…` |
| AC-6 | 발송 실패인데 OTP 저장 | 잡음 | `test_ac6_…` |
| AC-7 | 사용한 코드 재사용 허용 | 잡음 | `test_ac7_…` |
| AC-8 | 새 요청이 이전 코드를 무효화하지 않음 | 잡음 | `test_ac8_…`, `test_ac5_…` |
| AC-9 | 평문 코드를 그대로 저장 | 잡음 | `test_ac9_…` (외 5개) |

**심은 버그 11개를 전부 잡았고, 각 버그를 해당 AC의 테스트가 직접 잡았습니다.** (한 버그가 여러 테스트를 깨뜨리는 것은 AC들이 서로 연결되어 있어서 자연스럽습니다. 예: 코드를 4자리로 바꾸면 코드를 꺼내 쓰는 거의 모든 테스트가 영향을 받습니다.)

### 5. 테스트 설계에서 배울 점

- **시계를 주입(`FakeClock`)** — 실제로 5분을 기다리지 않고 `advance(300)`으로 "5분 뒤"를 만들어 만료를 검증합니다.
- **발송기를 주입(`FakeSender`, `FailingSender`)** — 진짜 SMS 없이 발송 성공·실패를 마음대로 만듭니다. 사용자가 문자로 받은 코드도 `FakeSender`가 기록한 메시지에서 꺼냅니다.
- **맞는 코드로 실패를 검증** — 만료·잠금 테스트는 일부러 *맞는 코드*를 넣어, "코드가 틀려서"가 아니라 "시간/횟수 때문에" 거절되는지 가려냅니다.
- **난수 고정(`monkeypatch`)** — 무작위 코드가 우연히 같아져 테스트가 가끔 깨지는(flaky) 일을 막기 위해 111111 → 222222로 고정합니다.
- **보안 함수** — 난수는 `secrets`(예측 불가), 비교는 `hmac.compare_digest`(응답 시간으로 코드를 추측하는 타이밍 공격 방어)를 씁니다.

### 6. 알려진 제약

| # | 제약 |
|---|---|
| 1 | 참조 구현은 **메모리 저장**입니다. 서버를 재시작하면 OTP가 사라지므로 실서비스는 Redis/DB가 필요합니다. |
| 2 | **실제 SMS/이메일 발송은 없습니다.** 발송기는 가짜 객체이며 실제 발송 서비스와의 연동은 검증하지 않았습니다. |
| 3 | **요청 횟수 제한(rate limit)이 없습니다.** OTP를 무한히 요청해 문자 비용을 유발하는 남용은 AC에 없고 막지 않습니다. |
| 4 | 시도 횟수는 **OTP 한 건 기준**입니다. 새 OTP를 요청하면 시도 횟수가 초기화되므로, 요청+시도를 반복하는 공격은 별도 정책(계정 단위 제한)이 필요합니다. |
| 5 | 등록되지 않은 사용자·연락처 검증, 동시 요청(여러 서버/스레드) 처리는 다루지 않았습니다. |
| 6 | 숫자 6자리·5분·3회는 **수업용 값**입니다. |
| 7 | 이 AC 번호(AC-1~9)는 `platform_spec.md`의 AC-1~33과 **번호가 겹치지만 별개**입니다. |
