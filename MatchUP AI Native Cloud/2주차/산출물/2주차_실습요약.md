## 2. 실습별 요약

### 2-1. SDD로 3-tier 데이터 플랫폼 구축

**실습 목표:** 명세를 먼저 쓰고 → 같은 3-tier 설계를 클라우드(Azure/Terraform)와 로컬(WSL2+Kubernetes)에 구성하고 → 데이터 품질 게이트를 붙여 명세 충족을 검증한다.

| 단계 | 목표 | 핵심 명령 | 산출물 | 검증 결과 (2026-10-19 재확인) |
|---|---|---|---|---|
| **1 · 명세** | 요구사항과 AC를 EARS로, AC마다 ID와 대상(클라우드/로컬/데이터) 표시 | — | [`spec/platform_spec.md`](../코드/spec/platform_spec.md) | AC **33개** (공통 5 · 클라우드 11 · 로컬 9 · 데이터 8) |
| **2 · 클라우드 IaC** | Azure 3-tier를 Terraform으로 선언 (`koreacentral`) | `terraform -chdir=infra init`<br>`terraform -chdir=infra validate`<br>`terraform -chdir=infra plan` | [`infra/`](../코드/infra/) 5개 `.tf` | `validate` **통과** · plan **21 to add, 0 change, 0 destroy** · ⚠️ **apply 안 함**(Azure에 아무것도 만들어지지 않음) |
| **3 · 로컬 K8s** | kind 클러스터에 web/api/db 배포, web만 NodePort | `kind create cluster --config k8s/kind-config.yaml`<br>`kubectl apply -f k8s/…`<br>`kubectl get pods,svc` | [`k8s/`](../코드/k8s/) 매니페스트 6개 · [`2-1_k8s_status.md`](./2-1_k8s_status.md) | 파드 **5/5 `Running 1/1`** · `localhost:8080/healthz/chain` **HTTP 200** (db 연결 ok) |
| **4 · 데이터 품질 게이트** | 결측·중복·IQR 이상치·범위 점검, 합격률 95% 미만이면 exit 1 | `python quality/validate.py quality/events.csv` | [`quality/validate.py`](../코드/quality/validate.py) · [`quality/events.csv`](../코드/quality/events.csv) | 합격률 **99.50% → PASS(exit 0)** · `--threshold 99.9` → **FAIL(exit 1)** |
| **마무리** | AC가 클라우드·로컬·데이터로 어떻게 충족됐는지 매핑 | — | [`2-1_sdd_report.md`](./2-1_sdd_report.md) | AC **33/33** 충족 (증거 수준은 아래 5절 참고) |

**추가로 만든 것 (요청 범위를 넘어 학습 효과를 위해):**
- 이미지 3개를 직접 빌드해 **Docker Hub**(`jjang404/matchup-w2-web|api|quality:1.2`, amd64+arm64)에 게시 → 클러스터가 그 이미지를 pull해 실행 ([`docker/`](../코드/docker/))
- web/api에 **헬스체크**(`/healthz`, `/healthz/chain`, `/api/livez`)와 계층별 상태 화면 → "무엇으로 ok라고 판단하는지"가 응답에 담김 ([`2-1_web_tier_guide.md`](./2-1_web_tier_guide.md))

**노트북 프롬프트의 명령과 실제로 쓴 명령의 차이**

| 노트북 프롬프트 | 이번 실습에서 | 이유 |
|---|---|---|
| `kind create cluster --name three-tier` | `kind create cluster --config k8s/kind-config.yaml` | web NodePort(30080)를 내 PC 8080으로 내보내는 설정이 필요 |
| `kubectl apply -f 2주차/코드/k8s/` | 파일을 하나씩 `apply` | 폴더째 적용하면 `kind-config.yaml`에서 `no matches for kind "Cluster"` 오류가 남(무해) |
| `terraform plan -out tf.plan` | `terraform plan` (비밀 값은 `TF_VAR_*` 환경변수) | plan 파일에 비밀 값이 남을 수 있어 저장하지 않음 |
| `python …/validate.py …/events.csv` | 동일 | 처음엔 `--csv`만 받아 오류가 났고, 이번에 **위치 인자도 받도록 고침** |

### 2-2. EARS 수용기준과 테스트 1:1 매핑

**실습 목표:** "OTP 로그인" 기능의 수용기준을 EARS로 쓰고, AC마다 pytest 테스트를 1:1로 만들어 모든 AC가 테스트로 커버되는지 확인한다.

| 항목 | 내용 |
|---|---|
| **목표** | OTP 로그인 AC 5개 이상(정상·만료·재시도 초과·잘못된 코드·발송 실패 포함) → pytest와 1:1 |
| **핵심 명령** | `python -m pytest tests/test_otp.py -v` · `python tests/check_coverage.py` · `python tests/make_mapping_table.py` |
| **산출물** | [`spec/ac_otp.md`](../코드/spec/ac_otp.md) · [`tests/test_otp.py`](../코드/tests/test_otp.py) · [`otp/otp_service.py`](../코드/otp/otp_service.py)(테스트 대상 참조 구현) · [`tests/check_coverage.py`](../코드/tests/check_coverage.py) · [`tests/make_mapping_table.py`](../코드/tests/make_mapping_table.py) |
| **검증 결과** | AC **9개** ↔ 테스트 **9개** 1:1, **9/9 통과**, 커버리지 **100%** · pytest **10 passed**(AC 9 + 추적성 검사 1) |

**OTP 수용기준 9개**

| ID | 케이스 | 한 줄 요약 | 테스트 함수 |
|---|---|---|---|
| AC-1 | 정상 · 발급 | 6자리 숫자 코드 생성·발송, `SENT` | `test_ac1_request_sends_six_digit_code` |
| AC-2 | 정상 · 검증 | 유효 시간 내 맞는 코드 → `OK` | `test_ac2_correct_code_authenticates` |
| AC-3 | 만료 | 300초 후에는 맞는 코드도 `EXPIRED` (299.9초 유효 / 300초 만료) | `test_ac3_expired_code_is_rejected` |
| AC-4 | 잘못된 코드 | `INVALID_CODE` + 남은 시도 횟수 | `test_ac4_wrong_code_is_rejected_with_remaining_attempts` |
| AC-5 | 재시도 초과 | 3회 실패 → `LOCKED`, 이후 정답도 거부 | `test_ac5_three_wrong_codes_lock_the_otp` |
| AC-6 | 발송 실패 | `SEND_FAILED`, 검증 가능한 OTP 미저장 | `test_ac6_send_failure_leaves_no_verifiable_otp` |
| AC-7 | 재사용 방지 | 사용한 코드 → `ALREADY_USED` | `test_ac7_used_code_cannot_be_reused` |
| AC-8 | 재요청 | 새 OTP 요청 시 이전 코드 무효화 | `test_ac8_new_request_invalidates_previous_code` |
| AC-9 | 평문 비저장 | 솔트+SHA-256 해시로만 저장 | `test_ac9_plain_code_is_not_stored` |

**"통과했다"를 믿을 수 있게 만든 장치**

| 장치 | 확인하는 것 | 결과 |
|---|---|---|
| 추적성 검사 (`test_every_ac_is_covered_by_exactly_one_test`) | pytest가 **실제로 수집한** 테스트의 마커 ↔ 명세 AC 표가 빠짐없이·겹치지 않게 대응 | 통과 |
| 변이 테스트 | 구현에 버그를 일부러 심었을 때 해당 AC 테스트가 실패하는가 | **11개 중 11개** 잡음 (임시 복사본에서만 실험) |
| 추적성 검사의 오류 시험 | 마커 삭제·주석 처리·`skip`·중복·명세 AC 추가·함수 이름 오타를 잡는가 | **전부** 잡음 |
| `check_coverage.py` | 명세·`ast`로 읽은 소스·pytest 수집 목록(텍스트/내부)을 교차 확인, "수집 목록 파싱 실패"를 스스로 진단 | 100%, 어려운 조건(CRLF·`-v` 설정·한글 경로)에서도 통과 |

> OTP의 AC 번호(AC-1~9)는 `platform_spec.md`의 AC-1~33과 **번호가 겹치지만 별개**입니다.

## 4. 배운 핵심 개념

### 4-1. SDD (Spec-Driven Development, 명세 우선 개발)

| | |
|---|---|
| **한 줄 정의** | 코드보다 **검증 가능한 명세를 먼저** 쓰고, 구현이 그 명세를 따르게 하는 방식 |
| **왜 필요한가** | "돌아간다 ≠ 맞다". 명세 없이 만들면 happy path만 동작하고 빠진 요구사항이 조용히 배포됨 |
| **명세 3요소** | 의도 · 수용기준(AC) · 제약 |
| **이번 실습** | `platform_spec.md` 하나에서 Terraform·K8s·품질 게이트가 모두 파생됨 → 명세가 단일 진실(SSOT) |
| **핵심 습관** | 완료 = "다 됐다"는 선언이 아니라 **게이트 통과**(exit 0, 테스트 통과)라는 명령 수준 증거 |

### 4-2. IaC / Terraform

| | |
|---|---|
| **한 줄 정의** | 인프라를 클릭이 아니라 **코드로 선언**해 재현 가능하게 만드는 것 (Infrastructure as Code) |
| **흐름** | `init`(준비) → `validate`(문법·구조 검사) → `plan`(**미리보기**: 무엇이 만들어질지) → `apply`(실제 생성) |
| **이번 실습** | 21개 리소스를 선언하고 `validate`·`plan`까지 확인. **`apply`는 하지 않음**(과금 방지, 사용자 확인 후 진행 원칙) |
| **좋은 습관** | 지역·접두어는 `variables.tf`로 분리 / 비밀번호·SSH 키는 기본값 없이 외부 주입 + `sensitive` / 버전 고정(`.terraform.lock.hcl`) |
| **주의** | `plan`이 통과해도 실제 배포 동작은 보장되지 않음 (이름 충돌·권한·쿼터는 `apply` 때 드러남) |

### 4-3. 3-tier 아키텍처

| | |
|---|---|
| **한 줄 정의** | 시스템을 **web(화면) → api(업무 로직) → db(데이터)** 3계층으로 나누는 구조 |
| **핵심 원칙** | ① 계층 간 **네트워크 분리** ② **최소 노출**: 외부에는 web만 열고 api·db는 닫음 ③ 인접 계층끼리만 통신(web→db 직접 접근 금지) |
| **같은 설계, 두 타깃** | |

| 관심사 | 클라우드(Azure) | 로컬(Kubernetes) |
|---|---|---|
| web | App Service | nginx Deployment + **NodePort** |
| api | VM Scale Set | node Deployment + ClusterIP |
| db | Azure SQL(+프라이빗 엔드포인트) | postgres StatefulSet + Headless |
| 계층 경계 | 서브넷 3개 | namespace 3개 + `tier` 라벨 |
| 통신 제한 | NSG | NetworkPolicy |
| 외부 노출 | web NSG의 Internet 허용 | NodePort(web만) |

### 4-4. Kubernetes

| 용어 | 쉬운 설명 | 이번 실습 |
|---|---|---|
| **파드(Pod)** | 컨테이너를 실행하는 가장 작은 단위. 죽으면 새로 만들어지고 이름·IP가 바뀜 | 5개 |
| **Deployment** | "이 파드를 N개 유지해 줘" | web·api (replicas 2) |
| **StatefulSet** | 파드 이름과 저장소를 **고정**. 데이터를 가진 서비스용 | db (`db-0`) |
| **Service** | 파드 앞의 **고정 주소**. 파드가 바뀌어도 이 주소로 찾아감 | web·api·db |
| **NodePort / ClusterIP** | NodePort는 클러스터 밖에서도 접속 가능, ClusterIP는 안에서만 | web만 NodePort |
| **namespace · label** | 클러스터 안의 구획과 꼬리표 | web/api/db, `tier` 라벨 |
| **probe** | 파드 상태를 주기적으로 확인. liveness(죽었나→재시작), readiness(트래픽 받아도 되나) | api는 둘 다 `/livez` |
| **NetworkPolicy** | 파드 간 통신 규칙(방화벽) | web→db 차단 |
| **kind** | Docker 컨테이너 안에 쿠버네티스를 만드는 로컬 실습 도구 | 클러스터 `three-tier` |

**실험으로 확인한 것:** db NetworkPolicy를 **지우면 web→db가 뚫리고(CONNECTED), 다시 적용하면 막힙니다(BLOCKED)** → 이 환경의 kindnet은 NetworkPolicy를 실제로 강제합니다.

**liveness와 healthz를 나눈 이유:** liveness가 실패하면 쿠버네티스가 파드를 **재시작**하므로 db 같은 의존 대상을 넣으면 db가 잠깐 느린 것만으로 api 전체가 재시작됩니다. 그래서 probe는 프로세스 생존(`/livez`)만 보고, db까지 포함한 `/healthz`는 사람이 보는 진단용입니다.

### 4-5. EARS 수용기준

| | |
|---|---|
| **한 줄 정의** | 요구사항을 `When <조건>, the system shall <결과>` 꼴의 **정형 문장**으로 쓰는 경량 문법 (Mavin, 2009) |
| **왜 필요한가** | "OTP를 안전하게 처리" 같은 모호한 문장은 테스트도 AI 파싱도 불가능. 언제·무엇을·몇 초/몇 회가 문장에 들어가야 테스트 1개로 직결됨 |

| 5패턴 | 형식 | 이번 실습의 예 |
|---|---|---|
| Ubiquitous | The system shall … | 모든 리소스는 `koreacentral`에 만든다 (AC-6) |
| Event-driven | When …, shall … | When a user requests an OTP, the system shall … (OTP AC-1) |
| State-driven | While …, shall … | (이번 실습에서는 사용하지 않음) |
| Optional | Where …, shall … | (사용하지 않음) |
| Unwanted | If …, then shall … | 합격률이 95% 미만이면 비정상 종료 (AC-32) |

**실습에서 얻은 교훈**
- **경계값을 명세에 못 박는다:** "5분 이내"만으로는 정확히 5분일 때가 모호. → 299.9초 유효, 정확히 300초 만료
- **AC ↔ 테스트 1:1**은 "테스트가 있다"만 보장. 테스트가 충분히 엄격한지는 **변이 테스트**(버그를 심어 보기)로 따로 확인
- **커버리지**(모든 AC에 테스트가 대응)와 **통과**(그 테스트가 성공)는 다른 말 — 버그를 심으면 커버리지는 100%로 남고 통과만 8/9로 떨어짐

### 4-6. 데이터 품질 게이트

| | |
|---|---|
| **한 줄 정의** | 데이터가 저장소에 들어가기 **전에** 품질을 점검하고, 기준 미달이면 파이프라인을 **중단**(exit 1)시키는 관문 |
| **왜 필요한가** | "Garbage in, garbage out" — 데이터 품질이 AI 결과 품질을 결정 |
| **합격률 계산** | `1 − 총 위반 건수 / (행 수 × 검사 항목 수)` → 200행 × 4검사 = 800 중 위반 4건 → **99.50%** |

**강의의 품질 5차원 ↔ 이번 구현**

| 5차원 | `validate.py`에서는 | |
|---|---|---|
| 완전성(결측 없음) | 필수 컬럼 결측률 < 5% (AC-26) | ✅ |
| 일관성·유일성 | `event_id` 중복 0건 (AC-27) | ✅ |
| 정확성(이상치) | `amount` IQR 경계 밖 값 (AC-28) | ✅ |
| 유효성(범위·형식) | `amount ≥ 0`, `event_type` 허용값 (AC-29·30) | ✅ |
| **최신성** | `event_ts`가 최근인지는 **검사하지 않음** | ❌ 미구현 |

**주의할 점:** 분모에 검사 수가 들어가서 위반이 **희석**됩니다. 위반이 1행에 몰려도 합격률이 높게 나올 수 있어 관대한 편입니다. "위반이 하나라도 있는 행의 비율"로 보려면 분모를 행 수로 바꿔야 합니다. 샘플의 99.50%는 위반을 **일부러 4건 심은** 데이터의 값이지 실데이터 품질이 아닙니다.

### 4-7. 그 밖에 배운 것

| 개념 | 요점 |
|---|---|
| **컨테이너 이미지·Docker Hub** | 이미지는 "실행 가능한 앱 꾸러미". `docker buildx`로 **amd64+arm64 멀티 아키텍처**를 올리면 Windows와 Apple Silicon Mac이 같은 태그를 쓴다. 파드의 `imageID` digest로 실제 실행 이미지를 확인 |
| **헬스체크 설계** | `200`/`503` 같은 코드가 곧 신호. 응답에 **판단 근거**(`how`, `method`, `latency_ms`)를 담아야 "무엇으로 ok인지" 알 수 있음 |
| **테스트 설계** | 시계·발송기를 주입해 실제로 5분을 기다리지 않고 만료·발송 실패를 검증, 난수를 고정해 flaky 방지, *맞는 코드*로 거절을 검증해 원인을 분리 |
| **증거 기반 보고** | 문서가 아니라 **실제 실행 결과**로 말한다. 같은 이름의 결과도 시점을 적는다 |

## 6. 알려진 제약과 정정 기록

### 6-1. 알려진 제약

| # | 제약 |
|---|---|
| 1 | **Azure에 배포하지 않았습니다.** `validate`·`plan`까지만 했고 클라우드 동작은 확인하지 못했습니다. |
| 2 | **클라우드 api VM에 앱이 없습니다.** VM Scale Set 정의에 앱 설치 코드가 없어, 배포하면 빈 Ubuntu VM만 생깁니다. |
| 3 | **db 점검이 TCP 수준입니다.** api는 db 포트 접속 가능 여부만 봅니다. SQL 실행 코드는 없습니다(읽기·쓰기는 `db-0` 안에서 `psql`로 따로 확인). |
| 4 | **데이터 적재가 없습니다.** CSV를 db에 넣는 단계가 없고, 품질 게이트는 CSV만 검사하는 독립 스크립트입니다. |
| 5 | **db 비밀번호가 매니페스트에 평문**입니다(로컬 실습용). 운영에서는 Key Vault 등을 써야 합니다. |
| 6 | **db 1개, 데이터는 클러스터에 종속**됩니다. `kind delete cluster` 하면 데이터도 삭제됩니다. |
| 7 | **진짜 고가용성이 아닙니다.** worker 2개는 같은 PC 안의 컨테이너입니다. HTTPS도 없습니다. |
| 8 | **NetworkPolicy는 들어오는 방향(Ingress)만** 제한합니다. |
| 9 | **WSL이 꺼지면 클러스터도 내려갑니다.** 다시 켜면 파드가 1~3분간 `Unknown`이고 RESTARTS가 오릅니다. 실습 중 컨트롤플레인 인증서가 손상돼 클러스터를 **10/18 하루에 2번**(19:33, 20:28) 새로 만들었습니다(10/15에 만든 것까지 합치면 지금 클러스터는 3번째). 현재 db-0의 RESTARTS 2는 이 때문입니다. |
| 10 | **Mac에서는 실행해 보지 못했습니다.** arm64 이미지는 올렸지만 실제 Mac 검증은 없습니다. |
| 11 | **OTP는 서버가 아닌 모듈**입니다. 메모리 저장이고 실제 SMS 발송이 없으며, 요청 횟수 제한(rate limit)이 없고 시도 횟수는 OTP 한 건 기준입니다. |
| 12 | **품질 게이트의 합격률이 관대한 편**(위반 희석)이고 **최신성 차원은 검사하지 않습니다.** |
| 13 | Docker Hub 이미지는 **공개 저장소**입니다. 샘플 CSV만 들어 있고 실제 고객 데이터는 없습니다. |

## 7. 3주차로의 연결 포인트

> **근거의 한계:** 읽은 자료에 3주차 상세 내용은 없고, 강의 자료의 한 줄("3주차 — AI 개발 기초·데이터 엔지니어링·임베딩")과 2주차의 데이터 파이프라인 슬라이드(수집→정제→변환→적재→피처/임베딩)뿐입니다. 아래는 **2주차 자산이 어떻게 이어질 수 있는지에 대한 제안**이며 3주차 확정 계획이 아닙니다.

**강의 자료의 파이프라인과 2주차의 위치**

```
수집(Ingest) → 정제(Clean) → 변환(Transform) → 적재(Load) → 피처/임베딩
                 ▲ 2주차 품질 게이트                  ▲ 2주차에서는 미구현(제약 #4)
```

| 2주차 자산 | 3주차(데이터 엔지니어링·RAG 전처리)에서의 쓰임 |
|---|---|
| **데이터 품질 게이트**(`validate.py`) | 문서·청크를 임베딩하기 **전에** 거르는 관문으로 확장: 빈 문서·중복 청크·길이 이상치·메타데이터 누락 점검. "기준 미달이면 exit 1" 패턴 그대로 |
| **품질 5차원** (특히 미구현인 **최신성**) | RAG에서는 오래된 문서가 답변 품질을 해치므로 문서 갱신 시각 검사가 필요 |
| **정제→변환→적재** 흐름 | 3주차의 변환=청킹·정규화, 피처/임베딩=벡터화. 2주차 4단계가 그 앞단(정제) |
| **적재 단계 부재**(제약 #4) | 정제한 데이터를 저장소(DB·벡터 저장소)에 **실제로 넣는** 단계를 채울 자연스러운 자리 |
| **로컬 K8s 3-tier + db 계층** | 벡터 저장소·임베딩 서비스를 db/api 계층에 올리는 실습 기반. postgres를 이미 쓰고 있어 벡터 확장(pgvector 등) 후보로 검토 가능 |
| **EARS 수용기준 + 테스트 1:1** | "When 질의가 들어오면, the system shall 상위 k개 청크를 반환한다" 같은 **검색 품질 AC**와 회귀 테스트셋으로 확장 |
| **헬스체크·관측성**(`/healthz`) | 파이프라인·인덱싱 작업의 상태·실패 원인 확인 |
| **SDD·단일 진실(SSOT)** | 전처리 규칙(청크 크기·필터 조건)을 코드가 아니라 명세에 먼저 기록 |
| **Docker 이미지·재현성** | 전처리 스크립트를 이미지로 묶어 Windows/Mac에서 같게 실행 (`quality` 이미지 방식 재사용) |

**3주차 시작 전에 해 두면 좋은 것**
1. 품질 게이트 합격률 계산의 희석 문제를 정하고(분모를 행 수로 할지), 최신성 검사를 추가할지 결정
2. 클라우드 api VM 앱 설치(제약 #2)와 db 적재 단계(제약 #4) 중 3주차에 이어 갈 것을 선택
3. 2-1 PDF 재변환, GitHub 업로드 구조(주차별 폴더) 확정 — 프로젝트 `CLAUDE.md` 7절 참고

## 8. 재현과 정리

**Windows(WSL2) / Mac 공통** — 모든 경로는 `2주차/` 기준입니다.

```bash
cd 2주차/코드

# (1) 데이터 품질 게이트
python quality/validate.py quality/events.csv ; echo "exit=$?"

# (2) OTP 수용기준 테스트
python3 -m venv .venv && source .venv/bin/activate && pip install pytest   # Windows: .venv\Scripts\activate
python -m pytest tests/test_otp.py -v
python tests/check_coverage.py

# (3) 로컬 3-tier
kind create cluster --config k8s/kind-config.yaml
for f in k8s/0*.yaml k8s/[1-4]0-*.yaml; do kubectl apply -f $f; done
for n in web api db; do kubectl wait --for=condition=Ready pods --all -n $n --timeout=300s; done
kubectl get pods,svc -n web -n api -n db
curl -s localhost:8080/healthz/chain

# (4) Terraform (plan까지)
cd infra
export TF_VAR_ssh_public_key="$(cat ~/.ssh/id_rsa.pub)"
export TF_VAR_sql_admin_password="<복잡한 임시 비밀번호>"
terraform init && terraform validate && terraform plan
```

**정리 (실습 후 반드시)**

```bash
kind delete cluster --name three-tier        # 로컬 클러스터 (db 데이터도 함께 삭제)
# terraform apply 를 했다면:  terraform -chdir=infra destroy
```
