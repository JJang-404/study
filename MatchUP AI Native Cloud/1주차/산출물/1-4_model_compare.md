## 2. 사전 작업 — 디스크 정리

실습 전 C: 여유가 9.4 GB뿐이라 모델을 받을 수 없었다. Ollama는 기본적으로 `C:\Users\<user>\.ollama\models`에 저장한다.

| 삭제 모델 | 크기 | 삭제 사유 |
|---|---|---|
| `gpt-oss:20b` | 13 GB | macOS 전용으로 역할 분리 (1-3 실습 3-1절) |
| `deepseek-r1:8b` | 5.2 GB | 한국어 질문에 영어로 응답 |
| `llama2:latest` | 3.8 GB | RAG를 "Requirements Attainment Gap"으로 오답 |

**결과: 22 GB 확보 (9.4 → 30.7 GB), 3종 pull 후 24.4 GB 잔여**

### ⚠️ 사고 기록 — `ollama rm` 중 다른 모델 손상

삭제 과정에서 `gemma3:12b`가 의도치 않게 깨졌다.

**경위:** `ollama rm` 실행 시 서버가 꺼져 있어 명령이 서버를 기동하며 멈췄고, 그 상태에서 서버를 하나 더 띄웠다. **ollama 서버 2개가 동시에 동작하며 blob 참조 카운팅이 꼬여**, 삭제 대상이 아니던 `gemma3:12b`의 blob까지 제거됐다.

manifest 무결성 검사 결과:

```
필요 blob: 5 / 존재: 1 / 누락: 4
```

**복구:** 깨진 manifest를 `ollama rm`으로 정리한 뒤 재다운로드(2.7분). 데이터 손실은 없었다.

**교훈: `ollama rm`은 서버가 정확히 하나만 떠 있을 때 실행한다.** 실행 전 확인:

```powershell
Get-Process ollama* | Select-Object Id,ProcessName   # Windows
```

```bash
pgrep -l ollama                                      # macOS
```

## 3. 2단계 — 동일 프롬프트 다중 모델 비교

프롬프트: **"RAG를 한 줄로 설명"**

### 3-1. 1차 측정 (콜드 — 모델 로딩 포함)

| 모델 | 지연(초) | 길이(자) | 응답 |
|---|---|---|---|
| `gemma3:12b` | 394.0 | 85 | RAG는 외부 지식 기반에서 정보를 검색하여 답변 생성 과정을 보충하는 AI 기술 ✅ |
| `llama3.2` | 15.7 | 112 | "그린 아웃 그루프(RAG)는 지역 소스에 기여하는… 유기농 농가…" ❌ |
| `qwen2.5` | 25.2 | 78 | RAG는 Retrieval-Augmented Generation의 약어로… ✅ |

### 3-2. 2차 측정 (웜)

| 모델 | 지연(초) | 길이(자) | 응답 |
|---|---|---|---|
| `gemma3:12b` | 50.1 | 90 | RAG는 기존 지식 기반에서 관련 정보를 검색… ✅ |
| `llama3.2` | 8.6 | 31 | "RAG는 라거리티 대피를 목적으로 하는 가방을 의미한다." ❌ |
| `qwen2.5` | 17.1 | 81 | RAG는 Retrieval-Augmented Generation의 약자로… ✅ |

### 3-3. ❌ `llama3.2`의 한국어 환각 — 3회 연속 전부 오답

같은 질문에 **매번 다른 엉뚱한 답**을 냈다.

| 회차 | 답변 |
|---|---|
| 1 | "그린 아웃 그루프 — 지역 유기농 농가 연결 활동" |
| 2 | "라거리티 대피를 목적으로 하는 가방" |
| 3 | "Regional Air Group — South Korea의 헬리콥터 연대" |

중국어 문자(`社区`)와 태국어 문자(`ิคอป`)까지 섞여 나왔다. **`llama3.2`(3B)는 한국어 작업에 사용 불가**로 판정한다.

> 속도는 가장 빨랐지만(8.6초) 답이 전부 틀렸으므로 의미가 없다. **품질 미달 모델의 속도는 측정할 가치가 없다.**

### 3-4. `gemma3:12b`가 웜에서도 느린 이유 — 모델 스래싱

1-3 실습에서 `gemma3:12b` 단독 측정 시 웜 7.7초였으나, 이번엔 50.1초로 **6배 이상 느려졌다.**

원인은 **메모리 부족으로 인한 모델 교체(thrashing)**다.

```
모델 3종 합계: 8.2 + 2.0 + 4.7 = 14.9 GB
시스템 RAM   : 15.8 GB (실사용 가능 ~9 GB)
```

3종을 번갈아 호출하면 매번 이전 모델을 메모리에서 내리고 다시 올린다. `OLLAMA_KEEP_ALIVE=30m`을 설정해도 **메모리가 부족하면 keep-alive와 무관하게 축출된다.**

> **벤치마크 설계 교훈:** 여러 모델을 순차 호출하는 비교는 단일 모델 성능을 측정하지 못한다. 모델별 실제 성능을 재려면 **한 모델씩 격리해 여러 번 호출**해야 한다.

## 4. 3단계 — 용도별 라우팅

### 4-1. 라우팅 규칙 (`router.py`)

| 작업 | 선택 모델 | 선택 근거 |
|---|---|---|
| `simple` | `llama3.2` | 가장 가벼움 — 짧은 요약에 큰 모델은 낭비 |
| `code` | `qwen2.5` | 코드 학습 비중이 높아 생성 품질이 좋음 |
| `general` | `gemma3:12b` | 기본값 — 한국어 품질과 속도의 균형 |

```python
def pick_model(task):
    model, _ = ROUTING_TABLE.get(task, ROUTING_TABLE["general"])
    return model
```

정의되지 않은 작업은 기본 모델(`general`)로 보낸다.

### 4-2. 실행 결과

| 작업 | 선택된 모델 | 지연(초) | 결과 |
|---|---|---|---|
| `simple` | `llama3.2` | 7.7 | ❌ "RAG(Regional Air Group)는 South Korea의 헬리콥터 연대…" |
| `code` | `qwen2.5` | 17.2 | ✅ 3가지 방식 제시 (`set`, 루프, `dict.fromkeys`) |
| `general` | `gemma3:12b` | 40.0 | ✅ 개인정보 보호 / 오프라인 사용 2가지 제시 |

**`qwen2.5`의 코드 응답이 특히 좋았다.** `list(set(lst))`를 제시한 뒤 **순서가 깨진다는 한계를 스스로 지적**하고, 순서를 유지하는 대안 2가지(루프, `dict.fromkeys`)를 추가로 제시했다. 요구사항을 넘어선 적절한 보완이다.

### 4-3. ⚠️ 라우팅 규칙의 결함 — "가벼운 모델 = simple 작업"은 틀렸다

`simple` 작업이 `llama3.2`로 라우팅되어 **오답을 반환했다.** "간단한 작업이니 가벼운 모델로"라는 직관이 깨진 것이다.

**간단한 작업이라고 모델 품질 요구가 낮아지는 것이 아니다.** "RAG를 한 줄로 설명"은 출력이 짧을 뿐, RAG라는 개념을 **정확히 알고 있어야** 답할 수 있다. 출력 길이와 필요 지식량은 별개다.

**수정된 라우팅 규칙:**

```python
ROUTING_TABLE = {
    "simple":  ("qwen2.5",    "최소 품질선을 넘는 가장 가벼운 모델"),
    "code":    ("qwen2.5",    "코드 생성 품질이 가장 좋음"),
    "general": ("gemma3:12b", "한국어 품질 우선"),
}
```

> 라우팅의 첫 기준은 "가벼움"이 아니라 **"해당 언어·도메인에서 최소 품질선을 넘는가"**다. 그 선을 통과한 모델 중에서 가벼운 것을 고르는 순서가 맞다.

## 5. 결론 — 어떤 작업에 어떤 로컬 모델이 적합한가

| 작업 유형 | 권장 모델 | 근거 |
|---|---|---|
| **한국어 일반 질의·요약** | `gemma3:12b` | 유일하게 일관된 고품질 한국어. 느리지만 정확 |
| **코드 생성** | `qwen2.5` | 한계까지 짚는 응답. 17초로 속도도 양호 |
| **빠른 응답이 필요한 영어 작업** | `qwen2.5` | 한국어도 가능하나 표현이 다소 어색 |
| **한국어 작업 전반** | ~~`llama3.2`~~ | **사용 금지** — 3회 연속 환각, 다국어 문자 혼입 |

### 종합 평가

| 모델 | 속도 | 한국어 | 코드 | 종합 |
|---|---|---|---|---|
| `gemma3:12b` | ★☆☆ | ★★★ | ★★☆ | 품질 우선 기본 모델 |
| `qwen2.5` | ★★☆ | ★★☆ | ★★★ | **가성비 최고 — 범용 권장** |
| `llama3.2` | ★★★ | ☆☆☆ | — | 한국어 부적합 |

**실용적 권장: 평소엔 `qwen2.5`, 한국어 품질이 중요할 때만 `gemma3:12b`.**
`qwen2.5`는 4.7 GB로 메모리 부담이 적어 스래싱도 덜 일으킨다.

## 6. 배운 점

- **모델 크기는 품질의 보증이 아니지만, 너무 작으면 확실히 무너진다.** 3B 모델은 영어권 벤치마크 점수와 무관하게 한국어에서 사용 불가 수준이었다. **다국어 성능은 별도로 검증해야 한다.**
- **"간단한 작업 = 작은 모델"은 위험한 단순화다.** 출력 길이와 필요 지식량은 별개 축이다. 라우팅 설계 시 작업의 *출력 규모*가 아니라 *요구 지식 수준*을 기준으로 삼아야 한다.
- **벤치마크는 측정 조건이 결과를 지배한다.** 같은 `gemma3:12b`가 7.7초(단독 웜)와 394초(콜드), 50.1초(스래싱)로 **50배 차이**를 보였다. 숫자를 인용할 때는 측정 조건을 반드시 함께 적어야 한다.
- **동시 실행 중인 서버 인스턴스는 상태를 손상시킬 수 있다.** `ollama rm`의 blob 참조 카운팅이 서버 2개 환경에서 꼬여 무관한 모델을 깨뜨렸다. 상태를 변경하는 명령 전에는 프로세스가 하나인지 확인하는 습관이 필요하다.

