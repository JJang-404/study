## 1. 핵심 용어 설명

### Temperature (온도)

LLM이 다음 단어를 고를 때 **얼마나 과감하게 선택하느냐**를 조절하는 값입니다.

| 값 | 동작 | 비유 |
|----|------|------|
| `0.0` | 항상 가장 확률 높은 단어만 선택 → 매번 같은 답 | 레시피 100% 충실 → 매번 똑같은 맛 |
| `0.7` | 적당히 무작위 → 자연스럽고 다양한 답 | 레시피 기본 준수 + 약간의 즉흥 |
| `1.2` | 매우 무작위 → 창의적이지만 엉뚱하거나 언어 혼용 | 레시피 무시, 즉흥 요리 → 가끔 이상한 맛 |

```
낮을수록 ──────── 높을수록
 일관성 ▶▶▶▶▶▶▶ 창의성
 재현성 ▶▶▶▶▶▶▶ 다양성
```

---

### Top_p (상위 확률 합계 / Nucleus Sampling)

LLM이 단어를 고를 때 **후보 목록의 크기**를 제한합니다.  
확률이 높은 단어들을 합산해 그 합이 `top_p`에 달할 때까지만 후보로 허용합니다.

| 값 | 동작 | 비유 |
|----|------|------|
| `1.0` | 모든 단어가 후보 (제한 없음) | 사전 전체에서 선택 가능 |
| `0.5` | 확률 합계 50%인 상위 단어들만 후보 | 자주 쓰는 단어 절반만 선택 가능 |

```
top_p 낮을수록 → 후보 풀 축소 → 더 안전하고 일반적인 답
top_p 높을수록 → 후보 풀 확대 → 더 다양한 표현 가능
```

> **temperature vs top_p**  
> temperature는 선택의 **과감함(확률 분포 형태)**을 바꾸고,  
> top_p는 선택할 수 있는 **단어의 범위(후보 수)**를 바꿉니다.  
> 둘 다 "다양성"에 영향을 주지만 작동 원리가 다릅니다.

## 2. 실험이란?

> **"같은 질문을 파라미터 값만 바꿔서 여러 번 돌려보고, 결과가 어떻게 달라지는지 비교하는 것"**

```
동일 질문: "여름 휴가 슬로건 한 줄 지어줘"
      │
      ├─ 조합 1: temperature=0.0, top_p=1.0  → 3회 호출 → 결과 비교
      ├─ 조합 2: temperature=0.7, top_p=1.0  → 3회 호출 → 결과 비교
      ├─ 조합 3: temperature=1.2, top_p=1.0  → 3회 호출 → 결과 비교
      ├─ 조합 4: temperature=1.0, top_p=0.5  → 3회 호출 → 결과 비교
      └─ 조합 5: temperature=1.0, top_p=1.0  → 3회 호출 → 결과 비교

목적: temperature·top_p 값이 응답 다양성에 얼마나 영향을 주나?
```

## 3. 실험 설계

| 항목 | 값 |
|------|-----|
| 모델 | `llama3.2:latest` (Ollama 로컬, 무료) |
| 엔드포인트 | `http://localhost:11434/v1` (OpenAI 호환) |
| 질문 | `"여름 휴가 슬로건 한 줄 지어줘"` |
| 반복 횟수 | 조합당 3회 |
| 총 호출 수 | 5개 조합 × 3회 = **15회** |
| 언어 강제 | 시스템 프롬프트 + 유저 메시지에 한국어 응답 지시 이중 적용 |

### 실험 조합

| # | temperature | top_p | 목적 |
|---|-------------|-------|------|
| 1 | 0.0 | 1.0 | temperature 최저 — 완전 일관성 확인 |
| 2 | 0.7 | 1.0 | temperature 기본값 |
| 3 | 1.2 | 1.0 | temperature 최고 — 최대 다양성 확인 |
| 4 | 1.0 | 0.5 | top_p 낮게 — 후보 풀 축소 효과 확인 |
| 5 | 1.0 | 1.0 | top_p 기본값 (조합 4와 비교 기준) |

## 4. 실험 결과

> **유사도(similarity)**: 3개 응답 간 평균 코사인 유사도.  
> 높을수록 응답이 서로 비슷 → **덜 다양**, 낮을수록 → **더 다양**  
> (단순 고유 응답 수로만 보면 판정이 틀릴 수 있어 유사도를 함께 계산함)

| 조합 | temperature | top_p | 고유 응답 | 평균 길이 | 유사도 | 중복도 | 평균 시간 |
|------|-------------|-------|---------|---------|------|------|---------|
| temp=0.0 / top_p=1.0 | 0.0 | 1.0 | **1/3** | 50.0자 | **1.000** | 완전중복 | 1.19s |
| temp=0.7 / top_p=1.0 | 0.7 | 1.0 | 3/3 | 16.7자 | 0.713 | 중간 | 0.35s |
| temp=1.2 / top_p=1.0 | 1.2 | 1.0 | 3/3 | 19.0자 | **0.337** | 낮음 | 0.39s |
| temp=1.0 / top_p=0.5 | 1.0 | 0.5 | 3/3 | 36.3자 | 0.676 | 중간 | 0.57s |
| temp=1.0 / top_p=1.0 | 1.0 | 1.0 | 3/3 | 15.3자 | 0.373 | 낮음 | 0.33s |

- 총 호출 수: **15회** (5개 조합 × 3회)
- 총 소요 시간: **14.7s**
- 호출당 평균: **0.33 ~ 1.19s**

## 5. 응답 미리보기

### temp=0.0 / top_p=1.0 — 완전중복 (유사도 1.000)
```
[1] 여름에 쫓겨난 나의 마음을 가득 담은 슬로건은 "여름이 오면, 내 마음도 여름이다"입니다.
[2] 여름에 쫓겨난 나의 마음을 가득 담은 슬로건은 "여름이 오면, 내 마음도 여름이다"입니다.
[3] 여름에 쫓겨난 나의 마음을 가득 담은 슬로건은 "여름이 오면, 내 마음도 여름이다"입니다.
```
→ temperature=0이면 LLM은 결정론적(deterministic)으로 동작 — 항상 완전히 같은 답

### temp=0.7 / top_p=1.0 — 중간 (유사도 0.713)
```
[1] "여름, 내 마음을 가슴에 쑜"
[2] "바루미, 보라미"
[3] "여름이 오면 바다에 가서 자lego!"
```
→ 표현이 달라지기 시작. 한국어 안정성은 보통 수준.

### temp=1.2 / top_p=1.0 — 낮음 (유사도 0.337) ← 가장 다양
```
[1] 여름에 오해를 주지 않아
[2] 바나ilha와 물로 쌀아오르다.
[3] 한달의 여름 휴가, 가을 기운, 남치던 추우러~.
```
→ 가장 다양하지만 외래어·무의미 문장 혼용 발생. 품질 불안정.

### temp=1.0 / top_p=0.5 — 중간 (유사도 0.676) ← top_p=1.0보다 덜 다양
```
[1] "여름에 내일이 더 오래되면, 내일은 오늘이 될 수 있다."
[2] "여름이 오면 나의 마음도 여름이 되고, 여름이 끝나면 나의 마음도 겨울이 된다."
[3] "夏에는 나를 이기다, 여름에는 나의 자신을 지키다."
```
→ top_p=1.0(유사도 0.373)보다 유사도가 높아 → 실제로 **덜 다양함** (고유 3/3이어도 내용이 더 비슷)

### temp=1.0 / top_p=1.0 — 낮음 (유사도 0.373)
```
[1] 한주 안에 여름을 기대한다.
[2] 여름이 오는 순간부터 여름을 즐기자
[3] "여름, 바다, 햇살"
```

## 6. 결론 및 실무 지침

### 이번 실험 한눈 정리

| 조합 | temperature | top_p | 고유 응답 | 평균 길이 | 유사도 | 평균 시간 |
|------|-------------|-------|---------|---------|------|---------|
| temp=0.0 / top_p=1.0 | 0.0 | 1.0 | **1/3** | 50.0자 | 1.000 | 1.19s |
| temp=0.7 / top_p=1.0 | 0.7 | 1.0 | 3/3 | 16.7자 | 0.713 | 0.35s |
| temp=1.2 / top_p=1.0 | 1.2 | 1.0 | 3/3 | 19.0자 | **0.337** | 0.39s |
| temp=1.0 / top_p=0.5 | 1.0 | 0.5 | 3/3 | 36.3자 | 0.676 | 0.57s |
| temp=1.0 / top_p=1.0 | 1.0 | 1.0 | 3/3 | 15.3자 | 0.373 | 0.33s |

> **핵심**: 고유 응답 수만으로는 부족 — 유사도를 함께 봐야 정확한 다양성 판정 가능

---

### 실험 데이터로 검증된 결론 3가지

**① temperature가 다양성의 주 제어 변수**

| temperature | 유사도 | 해석 |
|-------------|--------|------|
| 0.0 | 1.000 | 완전 동일 응답 — 재현성 100% |
| 0.7 | 0.713 | 다양하지만 품질 안정 |
| 1.2 | 0.337 | 가장 다양, 그러나 한국어 품질 저하 |

→ **temperature를 올릴수록 유사도가 감소(더 다양해짐)** — 유사도 변화폭 0.663

**② top_p는 temperature보다 영향이 작다**

| top_p (temperature=1.0 고정) | 유사도 | 해석 |
|------------------------------|--------|------|
| 0.5 | 0.676 | 후보 풀 축소 → 더 수렴 |
| 1.0 | 0.373 | 후보 풀 전체 → 더 다양 |

→ top_p 조정에 따른 유사도 변화폭 0.303 (temperature의 절반 수준)  
→ **temperature가 다양성에 2배 이상 강한 영향**을 미침

**③ 품질 한계선: temperature 1.0~1.2 구간에서 한국어 혼용 발생**

```
temp=1.2 응답 예시:
  "바나ilha와 물로 쌀아오르다."  ← 포르투갈어 혼입
  "한달의 여름 휴가, 가을 기운, 남치던 추우러~."  ← 무의미 나열
```

→ 다양성이 최대가 되는 지점(1.2)에서 **품질 안정성이 무너짐**

---

### 실무 지침 — 우리 데이터 근거 포함

> 강사님: "재현성이 필요한 추출·분류·요약은 temperature를 0 근처로,  
> 카피라이팅·아이디어 발산은 0.7~1.2 구간으로.  
> top_p는 temperature를 먼저 정한 뒤 미세 조정용으로 쓰는 편이 낫다."

우리 실험 결과가 이 지침을 어떻게 뒷받침하는지:

| 실무 상황 | 권장 temperature | 우리 데이터 근거 | top_p |
|-----------|-----------------|----------------|-------|
| 추출·분류·요약 (정답이 하나) | **0.0 ~ 0.3** | temp=0.0 → 유사도 1.000, 완전 재현 ✅ | 1.0 (영향 미미) |
| 일반 대화·번역·QA | **0.7** | temp=0.7 → 유사도 0.713, 3/3 고유, 한국어 안정 ✅ | 1.0 |
| 카피라이팅·슬로건·아이디어 발산 | **0.7 ~ 1.0** | temp=1.0 → 유사도 0.373, 다양성 확보 ✅ | 0.9~1.0 |
| 브레인스토밍 (품질보다 양이 중요) | **1.2** | 유사도 0.337 최저, 단 품질 불안정 ⚠️ | 1.0 |

**top_p 사용 원칙 (우리 데이터 기반)**

```
Step 1. temperature로 다양성 수준을 결정
          → temperature가 유사도에 2배 강한 영향 (실험 확인)

Step 2. top_p로 미세 조정
          → top_p=1.0 (기본값, 개방적)
          → top_p=0.7~0.9 (약간 보수적, 일반 대화에 적합)
          → top_p=0.5 (후보 풀 축소, 더 일관된 어조 필요 시)
```

---

### 우리 실험의 한계 — 더 실험이 필요한 부분

> "그냥 권장하고 끝내는 게 아니야? 실험을 더 해봐야 하는 거 아니야?"

맞습니다. 우리 실험에는 **명확한 한계**가 있습니다.

| 한계 | 이유 | 더 필요한 실험 |
|------|------|---------------|
| 질문 1개뿐 ("여름 휴가 슬로건") | 창의적 과제 1가지만 테스트 | 요약·추출·분류 과제에서도 동일하게 테스트 필요 |
| 품질을 점수로 측정 못 함 | 유사도는 다양성 지표, 정확성 지표가 아님 | 정답이 있는 과제(요약 정확도, 분류 F1)로 검증 필요 |
| 모델 1개(llama3.2) | 다른 모델은 temperature 민감도가 다를 수 있음 | GPT-4o, Claude Sonnet 등 동일 실험 반복 필요 |
| 반복 3회로 통계적 신뢰도 낮음 | 3회는 노이즈가 많음 | 조합당 10~20회로 평균·표준편차 측정 필요 |

**현재 우리가 말할 수 있는 것 (증거 있음)**
- temperature=0.0은 완전 재현 가능하다 (유사도 1.000)
- temperature를 올릴수록 다양성이 증가한다 (1.000→0.337)
- temperature=1.2에서 한국어 품질이 불안정해진다 (실제 응답 확인)
- top_p보다 temperature가 다양성에 더 큰 영향을 준다 (변화폭 비교)

**현재 우리가 아직 말하기 어려운 것 (데이터 부족)**
- "추출·분류 작업에서 temperature=0이 정확도가 더 높다" → 해당 과제 실험 없음
- "temperature=0.7이 최적 균형점이다" → 1개 창의적 질문 기준, 다른 과제 미검증
- "top_p는 항상 미세 조정 용도다" → 더 다양한 조합 실험 필요

## 7. 실제 모델 학습도 이런 방식으로 진행된다

> 강사님: "실제 모델들이 학습하는 방법도 이런식으로 진행된다"

**맞습니다.** 우리가 temperature·top_p를 바꿔가며 실험한 것처럼,  
실제 ML 모델 학습도 **하이퍼파라미터(Hyperparameter)** 를 바꿔가며 최적값을 찾습니다.

### 비교

| 우리 실험 | 실제 모델 학습 |
|---------|-------------|
| temperature 값을 바꿈 | learning rate(학습률)를 바꿈 |
| top_p 값을 바꿈 | batch size, dropout rate를 바꿈 |
| 3번씩 응답 수집 | 수십~수백 에폭(epoch) 학습 |
| 고유 응답 수·품질 비교 | 정확도(accuracy), 손실(loss) 비교 |
| 가장 좋은 조합 선택 | 가장 낮은 loss의 모델 저장 |

```
[우리 실험 흐름]
  파라미터 조합 설정
       ↓
  LLM 15회 호출
       ↓
```

## 8. 결과 검증(Validation)과 최적 모델 선정

> 강사님: "결과에 따라 결과 Validation을 해서 결과에 최적으로 나오는 모델을 지정하는 방식으로 하게 되어있다"

### 쉬운 설명

**Validation(검증)** = 실험 결과가 실제로 좋은지 객관적으로 확인하는 과정

비유: **요리사가 새 레시피를 개발할 때**
1. 여러 방법으로 요리 만들기 (실험)
2. 심사위원에게 맛 평가 받기 (Validation)
3. 가장 높은 점수 레시피를 공식 메뉴로 채택 (최적 모델 선정)

### 실제 흐름

```
[학습 데이터]          [검증 데이터]         [테스트 데이터]
 모델이 보고 학습      학습 중 성능 확인      최종 성능 평가
 (시험 공부)          (모의고사)            (실제 시험)
```

| 단계 | 역할 |
|------|------|
| Training | 모델이 데이터로 패턴 학습 |
| **Validation** | 학습 중 과적합 여부 확인, 하이퍼파라미터 튜닝 기준 |
| Test | 완전히 본 적 없는 데이터로 최종 성능 측정 |

### 우리 실험에서의 Validation

```
우리 실험의 Validation 기준:
  ✅ 한국어로 응답하는가?
  ✅ 고유 응답 수가 많은가? (다양성)
  ✅ 평균 응답 길이가 적당한가?
  ✅ 언어 혼용 없이 품질이 안정적인가?

→ 결론: temp=0.7 이 모든 기준에서 가장 균형 잡힌 최적 설정
```

## 9. A/B 테스트란?

> 강사님: "A/B 테스트라던지 A/B 테스트에 관해서도 다양한 A/B 테스트 형태가 있기 때문에 최적의 모델을 뽑아내는 부분도 모델 서빙에 있어서 가장 중요한 부분이다"

### A/B 테스트 기본 개념

**A/B 테스트** = 두 가지(또는 그 이상) 버전을 실제 사용자에게 동시에 보여주고,  
어느 쪽이 더 좋은지 데이터로 증명하는 방법

```
사용자 100명
   ├─ 50명 → [모델 A] (기존 temp=0.7)  → 만족도·클릭률·체류시간 측정
   └─ 50명 → [모델 B] (새 temp=0.9)   → 만족도·클릭률·체류시간 측정

결과: B가 만족도 12% 높음 → 전체를 B로 교체
```

### A/B 테스트의 다양한 형태

| 형태 | 설명 | 예시 |
|------|------|------|
| **기본 A/B** | 두 버전 50:50 분배 | 버튼 색 빨강 vs 파랑 |
| **A/B/C (다변량)** | 세 버전 이상 동시 비교 | temp=0.5 vs 0.7 vs 1.0 |
| **Canary 배포** | 새 모델을 5~10%에만 먼저 적용 | 새 LLM을 소수 사용자에 먼저 노출 |
| **Shadow Testing** | 새 모델이 실제 응답 안 하고 몰래 결과만 기록 | 프로덕션 트래픽으로 새 모델 성능 사전 측정 |
| **Interleaving** | 두 모델 결과를 섞어 보여주고 사용자가 어느 쪽 클릭하는지 관찰 | 검색 결과 A+B 혼합 노출 |
| **Multi-Armed Bandit** | 성능 좋은 버전에 자동으로 더 많은 트래픽 배분 | 광고 최적화, 실시간 모델 선택 |

### LLM 모델 서빙에서의 A/B 테스트 예시

```
[실제 서비스 예시 — 고객 응대 챗봇]

그룹 A (50%): GPT-4o, temp=0.7
그룹 B (50%): Claude Sonnet, temp=0.7

측정 지표:
  - 고객 만족도 (thumbs up/down)
  - 평균 대화 턴 수 (적을수록 빠른 해결)
  - 에스컬레이션율 (사람 상담원 연결 요청 비율)
  - 응답 속도 (latency)

2주 후 결과:
  A: 만족도 78%, 평균 4.2턴, 에스컬레이션 12%
  B: 만족도 84%, 평균 3.1턴, 에스컬레이션 8%
  → 전체 트래픽을 B(Claude Sonnet)로 전환
```

### 왜 모델 서빙에서 A/B 테스트가 중요한가?

> 실험실(offline) 성능 ≠ 실제 서비스(online) 성능

벤치마크에서 좋은 모델이 실제 사용자에게는 나쁠 수 있습니다.  
**A/B 테스트만이 "진짜 사용자 반응"을 데이터로 증명**할 수 있습니다.
