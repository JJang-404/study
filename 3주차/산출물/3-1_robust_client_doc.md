# robust_client.py 설계 문서

## 1. HTTP 429 Too Many Requests란?

외부 API 서버가 **"요청을 너무 많이 보냈으니 잠깐 기다려라"** 고 응답하는 상태 코드입니다.

```
HTTP/1.1 429 Too Many Requests
Retry-After: 2
```

### 발생 원인

| 상황 | 예시 |
|------|------|
| API Rate Limit 초과 | OpenAI: 분당 60 요청 한도 초과 |
| 동시 연결 수 초과 | 병렬 크롤링이 서버 임계치 돌파 |
| 일별/월별 쿼터 소진 | 클라우드 API 무료 티어 소진 |

### Retry-After 헤더

서버가 429를 돌려줄 때 **"이 시간(초) 뒤에 다시 와라"** 고 알려주는 헤더입니다.

```
Retry-After: 30   → 30초 후 재시도
Retry-After: 2    → 2초 후 재시도
```

헤더가 없으면 클라이언트가 알아서 대기 시간을 결정해야 합니다.

---

## 2. 왜 429를 4xx 영구 실패로 처리하면 안 되는가?

`4xx`는 보통 **"요청 자체가 잘못됐다"** 는 의미라 재시도해도 소용없습니다.  
그러나 429는 **"지금 당장은 안 된다, 나중에는 된다"** 는 의미입니다 — 일시 장애입니다.

```
400 Bad Request    → 요청 형식 오류 → 재시도 무의미 (영구 실패)
401 Unauthorized   → 인증 실패     → 재시도 무의미 (영구 실패)
404 Not Found      → 리소스 없음   → 재시도 무의미 (영구 실패)
429 Too Many Req.  → 속도 초과     → 기다리면 됨   (일시 장애) ✅
```

---

## 3. robust_client.py 의 처리 흐름

```
HTTP 응답 수신
      │
      ├─ 4xx (429 제외) ──────────────────→ ApiCallError 즉시 발생 (재시도 없음)
      │
      ├─ 2xx ─────────────────────────────→ JSON 반환 (성공)
      │
      └─ 429 또는 5xx (일시 장애)
              │
              ├─ 429 + Retry-After 헤더 있음 ──→ 헤더 값(초)만큼 sleep
              │
              └─ 429(헤더 없음) 또는 5xx ────→ 지수 백오프 + 지터로 sleep
                                               대기 = min(1s × 2^(attempt-1) + random(0~0.5s), 10s)
```

### 대기 시간 비교

| 시도 | 지수 백오프(기본) | Retry-After=2 |
|------|-------------------|---------------|
| 1회 실패 후 | 1.0s ~ 1.5s | **2.0s** (헤더 우선) |
| 2회 실패 후 | 2.0s ~ 2.5s | **2.0s** (헤더 우선) |
| 3회 실패 후 | ApiCallError | ApiCallError |

Retry-After가 있으면 서버가 지정한 값을 그대로 따릅니다. 서버가 "2초"라고 했는데 클라이언트가 4초 기다리는 것도, 0.5초만 기다리는 것도 모두 비효율적이기 때문입니다.

---

## 4. 지터(Jitter)를 추가하는 이유

지수 백오프만 쓰면 여러 클라이언트가 **동시에 실패 → 동시에 재시도** 하는 **천둥 떼(thundering herd)** 현상이 발생합니다.

```
지터 없음: 모든 클라이언트가 정확히 1s 후 동시 재시도 → 서버 또 과부하
지터 있음: 각자 1.0~1.5s 사이 무작위 대기 → 요청 분산
```

`random.uniform(0, 0.5)` 를 더해 최대 0.5초 범위에서 무작위로 흩뿌립니다.

---

## 5. 코드 핵심 구현 (robust_client.py)

```python
# 429 Retry-After 헤더 우선 적용
retry_after = resp.headers.get("Retry-After")
if resp.status_code == 429 and retry_after is not None:
    wait = float(retry_after)              # 서버 지정값 그대로 사용
else:
    wait = min(
        1.0 * 2 ** (attempt - 1)          # 지수 증가
        + random.uniform(0, 0.5),          # 지터
        10.0                               # 상한 10초
    )
time.sleep(wait)
```

## 6. 재시도 정책 요약표

| 상황 | 동작 | 이유 |
|------|------|------|
| ConnectionError | 재시도 (백오프+지터) | 네트워크 일시 단절, 복구 가능 |
| ReadTimeout | 재시도 (백오프+지터) | 서버 응답 지연, 복구 가능 |
| HTTP 429 + Retry-After | 재시도 (헤더 대기) | 속도 제한, 서버 지정 시간 후 가능 |
| HTTP 429 (헤더 없음) | 재시도 (백오프+지터) | 속도 제한, 대기 후 가능 |
| HTTP 5xx | 재시도 (백오프+지터) | 서버 일시 오류, 복구 가능 |
| HTTP 4xx (429 제외) | **즉시 ApiCallError** | 요청 자체 오류, 재시도 무의미 |
| max_retries 초과 | **ApiCallError** | 복구 불가 판단, 상위 레이어에 위임 |
