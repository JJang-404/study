## 1. 왜 LLM에 검색을 붙이는가

GPT-4나 Claude 같은 LLM은 학습 데이터를 바탕으로 답변을 생성합니다. 그런데 두 가지 근본적인 한계가 있습니다.

**첫째, 지식의 시간 한계.** 모델은 학습이 끝난 시점 이후의 정보를 모릅니다. 오늘 바뀐 정책, 어제 발표된 논문, 지난주 장애 보고서 — 모두 모릅니다.

**둘째, 지식의 범위 한계.** 인터넷에 공개되지 않은 사내 문서, 내부 규정, 특정 고객 데이터는 학습 데이터에 없습니다.

여기서 RAG(Retrieval-Augmented Generation)가 등장합니다. 핵심 아이디어는 단순합니다.

> "LLM에게 질문하기 전에, 관련 문서를 찾아서 함께 건네준다."

LLM을 재학습시키지 않고도 최신 정보를 활용할 수 있고, 답변에 근거(출처)를 명시할 수 있으며, 환각(hallucination)을 줄일 수 있습니다. 이것이 현재 기업에서 LLM을 실제로 활용하는 가장 일반적인 방식입니다.

## 2. 임베딩 — 텍스트를 숫자로 바꾸는 과정

컴퓨터는 텍스트를 직접 비교하지 못합니다. "강아지"와 "개"가 비슷한 의미라는 것을 단순 문자열 비교로는 알 수 없습니다. 임베딩(Embedding)은 이 문제를 해결합니다.

임베딩 모델은 텍스트를 고차원 숫자 배열(벡터)로 변환합니다. 이때 **의미가 비슷한 텍스트는 비슷한 벡터**가 되도록 학습됩니다.

```
"강아지" → [0.12, -0.45, 0.89, 0.03, ...]  (384개 숫자)
"개"     → [0.11, -0.47, 0.91, 0.02, ...]  (384개 숫자) ← 매우 유사
"자동차" → [-0.82, 0.23, -0.11, 0.67, ...] (384개 숫자) ← 매우 다름
```

### 이 실습에서 사용한 모델: all-MiniLM-L6-v2

- **출력 차원**: 384 (숫자 384개짜리 벡터 1개)
- **크기**: 약 90MB
- **특징**: Microsoft의 MiniLM 아키텍처를 사용해 BERT(768차원)를 절반 크기로 증류
- **처리 속도**: 빠름 (이 실습에서 14개 청크 임베딩에 0.41초)
- **용도**: 프로토타입, 영어 중심 문서에 적합

### 임베딩 모델이 학습되는 방식

임베딩 모델은 "이 두 문장은 의미가 같다/다르다"는 레이블 데이터로 학습됩니다. 학습 목표는 의미가 같은 문장 쌍의 벡터 거리는 가깝게, 의미가 다른 쌍의 거리는 멀게 만드는 것입니다. 이 과정을 대조 학습(Contrastive Learning)이라 합니다.

## 3. 벡터 공간 — 의미가 좌표가 되는 세계

384개의 숫자는 384차원 공간의 좌표입니다. 인간이 시각화할 수 없지만, 수학적으로는 일반 좌표계와 동일하게 다룰 수 있습니다.

2차원으로 단순화해서 이해해보면:

```
          의미 공간 (2D 단순화)
          
    동물 ↑
        │  [강아지]  [개]
        │      ●──────●
        │
        │              [고양이]
        │                  ●
        ├────────────────────────→ 생물
        │
        │  [자동차] [트럭]
    기계 │      ●──────●
```

비슷한 의미의 단어들이 공간에서 가깝게 모입니다. 실제 384차원에서도 이 원리는 동일합니다. "지수 백오프"와 "재시도 전략"은 가깝고, "지수 백오프"와 "코사인 유사도"는 멉니다.

---

## 4. 코사인 유사도 — 방향으로 의미를 비교한다

두 벡터가 얼마나 비슷한지 측정하는 방법으로 코사인 유사도를 사용합니다.

### 왜 유클리디언 거리가 아닌 코사인인가

유클리디언 거리는 벡터의 **크기(길이)**에 영향을 받습니다. 짧은 문장과 긴 문장은 내용이 같아도 거리가 달라질 수 있습니다. 코사인 유사도는 벡터의 **방향**만 비교하므로 문장 길이에 무관합니다.

```
코사인 유사도 = (A · B) / (|A| × |B|)

결과 범위:
  1.0 → 방향 완전히 같음 (의미 동일)
  0.0 → 직각 (관련 없음)
 -1.0 → 반대 방향 (의미 반대)
```

### 이 실습의 실제 스코어 해석

```
질의: "지수 백오프 재시도 thundering herd"

#1 청크7 (6절·HTTP 재시도 섹션) → 0.4959  ← 정확히 해당 내용
#2 청크13 (10절·모니터링)        → 0.3514  ← 0.14 낮음, 관련성 낮음
#3 청크9 (7절·ETL 변환)         → 0.2500  ← 거의 무관
```

0.5 미만으로 보이지만 이것은 all-MiniLM-L6-v2의 특성입니다. 이 모델은 절대 스코어보다 **상대적 순위**가 더 중요합니다. #1과 #2 사이 격차(0.14)가 명확하면 검색이 올바르게 동작한 것입니다.

## 5. 인덱싱 — 검색을 위한 사전 준비

인덱싱은 오프라인에서 미리 수행하는 단계입니다. 문서가 바뀌지 않는 한 한 번만 하면 됩니다.

```
원본 문서
    │
    ▼
[파싱] PDF/TXT/MD → 순수 텍스트
    │
    ▼
[청킹] 텍스트를 500자 단위로 분할 (50자 오버랩)
    │  → 각 청크에 {id, text, start, end} 메타 부여
    │
    ▼
[임베딩] 각 청크 → 384차원 벡터
    │  (all-MiniLM-L6-v2 모델 사용)
    │
    ▼
[저장] index.npy (벡터 행렬) + index_meta.json (메타데이터)
```

이 실습에서의 결과:
- `index.npy`: shape (14, 384) — 14개 청크 × 384차원, 21,632 bytes
- `index_meta.json`: 14개 청크의 텍스트와 위치 정보, 14,300 bytes

## 6. 검색 — 질의가 들어왔을 때 일어나는 일

사용자가 질의를 입력하면 온라인(실시간) 단계가 시작됩니다.

```
사용자 질의: "지수 백오프는 어떻게 동작하나?"
    │
    ▼
[질의 임베딩] 질의 → 384차원 벡터 (같은 모델 사용)
    │  query_vec = [0.23, -0.11, 0.67, ...]
    │
    ▼
[유사도 계산] query_vec와 인덱스의 모든 벡터 간 코사인 유사도 계산
    │  청크0: 0.29
    │  청크1: 0.31
    │  ...
    │  청크7: 0.50  ← 최고
    │  ...
    │
    ▼
[top-k 선택] 유사도 상위 3개 청크 반환
    │
    ▼
검색된 청크 텍스트 3개
```

**중요한 점**: 질의와 문서 청크를 **같은 임베딩 모델**로 변환해야 같은 벡터 공간에 놓이게 됩니다. 다른 모델을 쓰면 좌표계가 달라져 유사도 계산이 무의미해집니다.

## 7. 생성 — LLM이 답변을 만드는 방식

검색된 청크들을 LLM에게 컨텍스트로 제공합니다.

### 프롬프트 구조

```
[시스템 메시지]
당신은 주어진 컨텍스트를 바탕으로 질의에 답변하는 어시스턴트입니다.
컨텍스트에 없는 내용은 추측하지 말고 "모르겠습니다"라고 답하세요.

[검색된 컨텍스트 — top-3 청크 삽입]
--- 문서 1 ---
지수 백오프(Exponential Backoff)는 재시도 간격을 지수적으로 늘리는 전략입니다.
공식: 대기 시간 = base × 2^(attempt-1). base=1초로 설정하면 1초 → 2초 → 4초...

--- 문서 2 ---
(다음 청크 내용)

--- 문서 3 ---
(다음 청크 내용)

[사용자 질의]
지수 백오프는 어떻게 동작하나?
```

LLM은 이 전체 프롬프트를 읽고, 컨텍스트 내용을 근거로 답변을 생성합니다. 컨텍스트가 있기 때문에 "모르는 것을 지어내는" 환각이 줄어들고, 출처도 청크 ID로 추적할 수 있습니다.

### 이 실습은 생성 단계까지 포함하지 않는다

이 실습은 "검색(Retrieval)" 전처리까지입니다. 생성 단계는 4주차에서 OpenAI API 또는 Azure OpenAI를 연결해 완성합니다.

## 9. 품질을 높이는 핵심 설계 결정들

### 청크 크기 선택

| 청크 크기 | 효과 | 주의 |
|-----------|------|------|
| 너무 작음 (< 100자) | 정밀하지만 문맥 없음 | 답변 생성에 필요한 정보가 분산됨 |
| 적절 (200~600자) | 균형 | 도메인에 따라 실험 필요 |
| 너무 큼 (> 1000자) | 문맥 풍부 | 노이즈 포함, 임베딩 품질 하락 |

오버랩(overlap)은 문장이 청크 경계에서 잘리는 것을 방지합니다. 50~100자가 일반적입니다.

### 임베딩 모델 선택

| 선택 기준 | 추천 모델 |
|-----------|-----------|
| 빠른 프로토타입 | all-MiniLM-L6-v2 (384차원, 90MB) |
| 더 높은 품질 | all-mpnet-base-v2 (768차원, 420MB) |
| 한국어 특화 | jhgan/ko-sroberta-multitask |
| 최고 품질 (유료) | OpenAI text-embedding-3-small |

### top-k 선택

- k가 작으면 (k=1~3): 정밀도 높음, 관련 내용 누락 위험
- k가 크면 (k=10~20): 재현율 높음, 노이즈와 토큰 비용 증가
- 실제 시스템: k=10~20으로 넓게 검색 후, 리랭킹(cross-encoder)으로 top-3~5 선별

### 스코어 임계값 설정

유사도가 너무 낮은 청크는 반환하지 않는 것이 좋습니다. 예를 들어 코사인 유사도 0.3 미만이면 "관련 문서 없음"으로 처리해 LLM이 잘못된 근거로 답변하는 것을 막을 수 있습니다.

## 10. 이 실습에서 실제로 일어난 일

### 1차 실행 (샘플 문서 너무 작음)

```
문서 크기: 1,082자  →  청크 3개
top-3 스코어: 0.40 / 0.40 / 0.27
문제: top-3 = 전체 100% → 검색의 의미 없음
     스코어 차이 거의 없음 → 변별력 없음
```

### 2차 실행 (문서 확장 후)

```
문서 크기: 5,966자  →  청크 14개
top-3 스코어 예시 (지수 백오프 질의): 0.496 / 0.351 / 0.250
개선: top-3 = 전체 21% → 실제 선별 의미 있음
     #1과 #2 격차 0.14 → 명확한 1위
```

### 판단 기준 정리

좋은 RAG 검색의 신호:
1. **top-k << 전체 청크 수** (top-3/전체가 50% 이하)
2. **#1 스코어가 #2보다 명확히 높음** (0.05 이상 차이)
3. **#1 청크가 실제로 질의와 관련 있음** (사람이 봐도 맞는 섹션)
4. **다른 주제의 질의는 다른 청크가 #1이 됨** (섹션별 변별)
