### 발견한 문제
1. **샘플 문서가 너무 작다** (2,130 bytes / 1,082자 / 33줄)
   - size=500, overlap=50 기준 → 청크 **3개**만 생성
   - top-k=3 검색이 사실상 **전체 문서 반환**과 동일 → 검색의 의미 없음
   - 유사도 스코어: 0.3987 / 0.3962 / 0.2715 → 거의 균등 → **변별력 없음**

2. **좋은 RAG 샘플의 기준**
   - 청크 수: 최소 15개 이상 (top-3가 전체의 20% 이하여야 의미 있음)
   - 내용 다양성: 주제별로 명확히 구분되어야 질의마다 다른 청크가 검색됨
   - 예) "지수 백오프 재시도" 질의 → API 재시도 관련 청크만 hit
         "임베딩 차원" 질의 → 벡터/임베딩 청크만 hit

3. **목표**
   - 샘플 문서: ~8,000자 이상 → 청크 약 16~18개
   - 주제를 최소 5개 섹션으로 분리 (RAG 개요 / HTTP 재시도 / 데이터 파이프라인 / 임베딩/벡터 / 클라우드 AI)
   - 검색 시연 질의도 각 섹션에 매핑되는 것으로 선택해야 함

- `all-MiniLM-L6-v2`는 영어 중심 학습 → 한국어를 알 수 없는 토큰으로 처리
- 한국어 문장들이 임베딩 공간의 좁은 영역에 뭉쳐버림

### 하이브리드 검색 효과 검증

**질의: "지수 백오프 재시도 전략"**

| 모드 | #1 | #2 | #3 |
|------|----|----|-----|
| semantic | 청크08 ✅ | 청크12 ❌ | 청크07 ✅ |
| hybrid | 청크08 ✅ | 청크07 ✅ | 청크12 ❌ (하락) |

→ 하이브리드가 오탐(청크12)을 밀어내고 실제 관련 청크07을 2위로 올림.

### BM25 한국어 문제와 해결

- **문제**: `.split()` 공백 분리 → `재시도해도` ≠ `재시도`, BM25 매칭 실패 → IDF 노이즈 랭킹 → RRF 오염
- **해결**: 한글 포함 시 문자 2-gram 토큰 추가
  ```python
  stripped = text.replace(" ", "")
  bigrams = [stripped[i:i+2] for i in range(len(stripped) - 1)]
  tokens = text.split() + bigrams
  ```
- **한계**: 형태소 분석기(KoNLPy, Mecab) 없이는 완전한 해결 불가. 일부 오탐 잔존.

### 남은 개선 포인트
- 청크 경계가 섹션 중간에 걸리는 경우 있음 (청크8이 6절 끝+7절 시작을 동시에 포함)
  → 의미 기반 청킹(Semantic chunking)으로 개선 가능, 현 실습 범위 밖
- "핵심 개념 한 줄" 같은 추상적 질의는 여전히 변별력 낮음 (0.39)
  → 의도가 명확한 질의일수록 RAG가 잘 동작함을 실습에서 확인
